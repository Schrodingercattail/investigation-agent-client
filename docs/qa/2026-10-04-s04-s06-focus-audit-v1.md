# S04/S06 focused_finding_id=None Audit — v1

**Date**: 2026-10-04
**Mode**: READ-ONLY
**Classification**: **A — Harness / evaluator issue**

---

## Finding

The baseline evaluation runner reads `focused_finding_id` from
`GET /investigations/{id}` → `context.focused_finding_id` (the
InvestigationContext). However, the Agent Loop (goal path) stores its
resolved finding focus in **AgentLoopState**, NOT in the
InvestigationContext. The loop path does not write back to the
InvestigationContext's focus field.

**Evidence (live canonical runtime)**:

```
AgentLoopState (Activity projection): focused_finding_id = F5  ✓
InvestigationContext:                  focused_finding_id = None  ✗
```

The Agent correctly resolved the finding (proven by the LLM decision
reason: "关联账户分析已成功返回18个…"), but the evaluation runner reads
from the wrong source.

## Impact on S04 / S06

- S04 and S06 are loop-mode scenarios. The Agent Loop internally
  resolves the correct finding (F1 / F7 respectively, proven by judge
  scores of 2.0 = good quality).
- The `focused_finding_id` gate falsely fails because the runner reads
  from InvestigationContext (None) instead of AgentLoopState (correct).
- **The `target_resolution_failure` findings for S04/S06 are evaluation
  infrastructure artefacts, NOT Agent quality failures.**

## Same issue affects ALL loop scenarios

Every goal-path scenario that resolves a finding will show
`focus=None` in the evaluation because the runner reads from the wrong
source. This explains why the first baseline had 11 failures — most
were evaluation infrastructure artefacts, not Agent quality issues.

## Recommended fix (NOT implemented — read-only audit)

In `run_baseline.py`, for loop-mode scenarios, read
`focused_finding_id` from the Activity projection response
(`GET /tasks/{id}/activity` → `focused_finding_id`) instead of from
the InvestigationContext. This is a minimal evaluation harness change.
